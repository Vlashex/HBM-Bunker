# Работа над сборкой

Основная ветка — `main`. Тег `v0.1.0-mvp` фиксирует исходную версию проекта.
Небольшие изменения удобно делать в ветках `feat/<тема>`, исправления —
в `fix/<тема>`. Готовую правку объединяй в `main` после соответствующей проверки.

## Обычное изменение

1. Измени файлы в `pack/patch/` или `pack/config/`. Это канонические исходники.
2. При смене состава обнови `metadata/mods.lock.json`: точная версия, URL,
   размер и SHA-256. Сохрани нужные зависимости и загрузчик NeoForge.
3. Если затронуты сита/EMC, обнови соответствующие справочные JSON в `metadata/`.
4. Опиши поведение в `CHANGELOG.md` → `Unreleased`; обнови документацию баланса.
5. Запусти тесты Python, `check` и сборку; проведи игровую проверку изменённой механики.
6. Укажи в коммите, что изменилось и как проверено. Не выдавай старый отчёт за новый.

Запуск инструментов: `python -m unittest discover -s tests -v` и
`python tools/release.py check`. Полная упаковка: `python tools/release.py build`.

## Когда нужна игровая проверка

| Изменение | Проверка |
|---|---|
| Рецепты | JEI и реальный крафт: выход, количество, компоненты, старые обходы |
| Новые моды | Клиент и отдельный тестовый мир; зависимости и совместимость |
| Дроп/Удача | Сравнение без Удачи, III/V и Silk Touch; достаточная выборка |
| EMC | Цены разрешённого сырья, отсутствие стоимости у запрещённых технологий |
| Автоматизация | Работающая установка, питание, вход и выход предметов |
| Только документация/упаковка | Проверки инструмента и целостности архива |

Миры для испытаний создаются отдельно от игровых сохранений.
Серверные EULA и пользовательские аккаунты не включаются в релиз или Git.

## Java-мод Dead Earth

Координатор находится в `mods/dead-earth/`; это отдельный Gradle-проект, а не часть
lowcode-патча рецептов. Требуется Java 21. Сначала `python mods/dead-earth/bootstrap.py`,
затем из папки мода `./gradlew.bat test build` и `./gradlew.bat runGameTestServer`.
Wrapper JAR скачивается по закреплённому commit и проверяется по SHA-256;
игровые библиотеки и результаты сборки остаются вне Git.

Серверные часы и Scenario Engine проверяются также после сохранения/перезапуска
в отдельном мире. Состояние `RUNNING` после загрузки не повторяется автоматически.
Историческая проблема ProjectE и проверка её исправления описаны в
[Foundation](docs/DEAD-EARTH-VERIFICATION.md) и
[Expeditions](docs/DEAD-EARTH-EXPEDITIONS-VERIFICATION.md).

Дальнейшая разработка ведётся непрерывными срезами: коммиты не требуют полного
прогона клиента/сервера каждый раз. Накапливай связный набор изменений, затем
проводишь общий прогон. Для независимых GameTest испытаний задавай новую папку
через `-PdeadEarthGameTestDirectory=run-gametest-<проверка>`.

Собственные JAR включаются по `metadata/own-mods.lock.json`; сначала собери Java-мод,
затем обнови размер/хеш и упакуй. Сборщик проверяет также modId, версию и класс входа.

## Выпуск версии

1. Выбери номер в `release.json`, например `0.1.1` для исправлений или `0.2.0`
   для следующего этапа. Изменение играбельного содержимого получает новый релиз.
2. Если меняется патч, согласованно обнови `patch_version`, `patch_filename`
   и версию в `pack/patch/META-INF/neoforge.mods.toml`.
3. Перенеси `Unreleased` в раздел нового релиза, укажи дату.
4. Создай `docs/releases/<version>.md`: изменения, установка, миграция, проверки,
   ограничения. Для изменений мира/генерации явно опиши совместимость сохранений.
5. Собери архив, проверь SHA-256 и запуск в PrismLauncher на отдельном профиле.
6. Сделай коммит, проверь чистоту Git и создай аннотированный тег:

```sh
git tag -a v<VERSION> -m "HBM Bunker <VERSION>"
```

Теги уже выпущенных версий не перезаписывай. Исправление выпускается новым тегом.
Готовый ZIP, JAR патча и SHA256SUMS — артефакты выпуска; в Git хранятся исходники.
Удалённый репозиторий пока не настроен. Публикация и отправка коммитов выполняются отдельно.
