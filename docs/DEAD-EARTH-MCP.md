# DEAD EARTH — контракт сценариев и MCP

Статус: проект интерфейсов от **16 октября 2026**, к [основному roadmap](DEAD-EARTH-ROADMAP.md).
Имена инструментов, схемы и значения ниже предлагаются для разработки; действующего
MCP-мост с семью узкими инструментами и безопасным сигналом реализован отдельно:
см. [текущую реализацию](DEAD-EARTH-MCP-BRIDGE.md). Остальные операции ниже,
атакующие сценарии биосфер, многошаговые планы и ИИ остаются проектом.

Обновление 17 октября 2026: ближайший порядок и распределение полномочий описаны в
[архитектуре режиссёра](DEAD-EARTH-DIRECTOR.md). Модель не задаёт численность,
координаты и силу атаки; прежние предложения ниже об адаптации количества
не используются как разрешение. MCP сейчас ограничен реализованным каталогом.

## 1. Архитектура управления

```text
OVERSEER: локальный host с MCP-клиентом и моделью
    → Python MCP-сервер: инструменты, память, проверка формы
    → локальный аутентифицированный мост
    → Java Dead Earth: ARBITER → очередь → Scenario Engine
    → адаптеры Overgrown / Mutationcraft / HBM
```

Модель сама по себе не является MCP-клиентом: host выбирает инструменты,
передаёт результаты модели и управляет циклом. MCP задаёт формат обмена, а правила
игровой власти реализуем мы. Основание:
[архитектура MCP](https://modelcontextprotocol.io/specification/2025-11-25/architecture),
[инструменты и JSON Schema](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

На одном ПК предпочтителен MCP через stdio между host и gateway. Bridge до Java
слушает только loopback с токеном процесса. При самостоятельном HTTP MCP-сервисе
нужны аутентификация, проверка Origin и границ запросов; наружу он не публикуется.
Версии SDK и поддерживаемого протокола закрепляются при реализации.
Источник: [транспорты MCP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Сетевой поток принимает ограниченное сообщение и ставит неизменяемый запрос в
очередь. Проверка игрового состояния и работа с миром выполняются в серверном
потоке; снимки выдаются из кеша. Никаких запросов модели или чтения всего мира
из HTTP-потока. Основание для поточной границы:
[NeoForge 1.21.1 networking](https://docs.neoforged.net/docs/1.21.1/networking/payload/).

Готовый [MCPFabric](https://github.com/denfry/mcpfabric) поддерживает в том числе
NeoForge 1.21.1 и может быть образцом транспорта. Однако предоставляемые им
операторские команды и прямое редактирование мира существенно шире требуемых
полномочий директора. Аналогично обычный RCON-MCP не превращается автоматически
в каталог игровых сценариев. Их нельзя выдавать OVERSEER целиком.

## 2. Что именно ИИ может редактировать

Есть три уровня:

1. **Шаблон сценария** — проверенный разработчиком набор примитивов в Git.
   У него фиксированные допустимые цели, пределы, предвестники и последствия.
2. **Вариант** — разрешённые настройки шаблона: состав из утверждённого пула,
   направление, интенсивность в диапазоне, окно времени, условия отмены.
3. **Операция** — небольшой граф экземпляров: подготовка, отвлечение, основное
   действие, ветви реакции и завершение. Глубина и число шагов ограничены политикой.

OVERSEER выбирает шаблон, редактирует вариант и связывает шаги операции.
Увеличение числа мобов до разрешённой верхней границы — допустимо; добавление
нового типа ядерного взрыва, произвольного NBT или команды в текстовом поле — нет.
Для нового примитива требуется обычное изменение кода и тесты. Позднее можно
позволить модели составлять черновики новых шаблонов из уже разрешённых примитивов,
но это не расширяет исполняемые полномочия автоматически.

## 3. Начальный каталог

| Шаблон | Разрешённая адаптация | Предвестник и противодействие | Особая проверка |
|---|---|---|---|
| `parasite_scouts_v1` | Точка из подходящих якорей, пул разведчиков, размер группы | Следы/звуки, уничтожение разведки | Путь до цели, стадия Mutationcraft, общий лимит популяции |
| `parasite_siege_v1` | Направление, состав волн, интервалы | Маяк/скопление, возможность сорвать подготовку | Возврат вещей после смертей, бюджет осад, оборона команды |
| `spore_front_v1` | Регион, длительность, плотность в пределах | Изменение неба/датчик, фильтры, уничтожение источника | Временный эффект не оставляет вечный накопительный бонус |
| `forest_diversion_v1` | Один ложный фронт и одна настоящая цель | Наблюдаемая активность; разведка раскрывает план | Оба фронта учитываются в одном бюджете |
| `false_spring_v1` | Продление CALM в разрешённом окне | Аномальный прогноз, биологические признаки | Минимум передышки после зимы сохраняется; нельзя скрыть обязательный сигнал катастрофы |
| `recovery_window_v1` | Продолжительность и разрешённые будущие паузы | Читаемое снижение давления | Не удаляет чужих мобов и последствия уже совершённого взрыва |
| `meteor_strike_v1` | Проверенная зона падения и фиксированный профиль размера | Наблюдаемый след/предупреждение, эвакуация | Весь коридор падения, кратер, вторичные эффекты и нагрузка |
| `bunker_incident_v1` | Один зарегистрированный заброшенный объект, профиль аварии | Телеметрия нестабильности, возможность отключить узел | Влияние на игроков, соседние объекты, радиация и цепные реакции |

Первые автоматические события — разведчики, временный фронт спор, отвлечение
и передышка. Метеорит и нативный ядерный взрыв включаются отдельными возможностями
только после успешного измерения каждого профиля. Нельзя открывать их одним
универсальным параметром «сила 0…1000».

«Взрыв заброшенного бункера» имеет два разных профиля. Облегчённый — заранее
подготовленная разрушенная структура, локальные визуальные эффекты и ограниченное
загрязнение. Нативный — настоящий проверенный взрыв HBM со всеми последствиями.
Первый не выдаётся за физически полный второй; он доступен раньше, если настоящую
катастрофу пока нельзя безопасно ограничить или компьютер её не выдерживает.

## 4. MCP-инструменты

| Инструмент | Возвращает / изменяет |
|---|---|
| `get_snapshot` | Краткий снимок: стадия, климат, известные регионы, нагрузка, состояние команды |
| `list_catalog` | Только доступные шаблоны, диапазоны, требования, причины блокировки |
| `get_history` | Факты и исходы по ограниченному фильтру, с источником и временем |
| `preview_scenario` | Расчёт допустимости, стоимости, зоны влияния, рисков и отказов; ничего не запускает |
| `propose_scenario` | Предложение в очередь ARBITER; возвращает `scenario_id` или причину отказа |
| `update_pending_scenario` | Новая ревизия ещё не исполненных шагов в тех же пределах |
| `get_scenario_status` | Достоверное состояние и квитанции исполнения |
| `cancel_pending_stages` | Отмена будущих шагов конкретного сценария с новой ревизией |

У MCP нет `run_command`, `eval`, shell, чтения произвольных файлов, записи конфигов,
сырого изменения инвентаря/здоровья, произвольных координатных взрывов и `purge` всех
мобов. Администраторские средства диагностики существуют отдельно и не перечисляются
модели как инструменты.

Предложение для `propose_scenario`:

```json
{
  "request_id": "uuid",
  "world_epoch": "campaign-session-uuid",
  "expected_campaign_revision": 42,
  "catalog_id": "parasite_scouts_v1",
  "catalog_version": 1,
  "target_region_id": "north_road_03",
  "earliest_campaign_tick": 144000,
  "expires_campaign_tick": 168000,
  "parameters": {
    "composition_id": "early_scouts",
    "direction": "north",
    "intensity_multiplier": 0.95
  }
}
```

Идентификатор цели выбирается из подходящих известных регионов. Координаты
разрешённых якорей и полный след воздействия определяет сервер, не текст модели.
Доступные параметры и их диапазоны задаёт JSON Schema каждого шаблона.
Клиентские версии и ревизии — защита от устаревшего решения, а не основание доверять
ему: предложение всегда перепроверяется по текущему миру.

Ответ содержит `scenario_id`, `instance_revision`, состояние, принятые параметры,
зарезервированный бюджет и структурированные причины отказа/отсрочки.
Модель может исправить предложение в пределах каталога. Отказ по защите территории
не даёт ей новый инструмент для обхода защиты.

## 5. ARBITER и игровые пределы

Порядок проверки:

1. Формат, размер сообщения, токен, `request_id`, совместимость каталога.
2. Кампания и эпоха, допустимость цели и состояние её чанков.
3. Стадия, климатическое окно, онлайн-игроки, восстановление команды.
4. Общие популяционные и событийные лимиты, охлаждение, исключение конфликтов.
5. Полная пространственная область влияния, защищённые зоны и допустимый профиль.
6. Резервирование бюджета и сохранение записи перед постановкой на исполнение.
7. Повторная проверка текущей ситуации перед каждым существенным шагом.

«Заброшенный» — свойство зарегистрированного объекта, а не утверждение ИИ.
Учитываются проживание и недавние действия игроков, размещённые блоки, контейнеры,
регистрация/защита территории и запас расстояния. Для HBM учитываются разрушение,
осадки, радиация и возможные вторичные реакции. Проверка центра точки недостаточна.
Если область влияния нельзя достоверно ограничить, профиль не допускается.

Начальный бункер имеет период восстановления и защиту от сценарного прямого
уничтожения. Осадные мобы могут атаковать подходы и разрешённые укрепления в рамках
политики кампании. Взрывы и команды не обходят SecurityCraft. Такая политика
публикуется как правила кампании; подтверждать каждый разрешённый спавн вручную
не требуется.

Существенное стратегическое усиление OVERSEER возможно только внутри ограничений
шаблона. Итоговый бюджет считает базу, климат, число активных игроков, вариант
сценария и WARDEN, затем применяет жёсткий верхний предел. Нельзя бесконечно
перемножать несколько независимых коэффициентов без общей границы.

Сущности получают атрибуцию сценария. Лимит учитывает превращения, потомков
и взаимодействие с естественными спавнами. Очистка касается только собственных
временных сущностей по правилам шаблона; не уничтожает всех заражённых мира.

## 6. Исполнение, сбои и отмена

Состояния: `draft → validated → scheduled → signaled → running → completed`.
Дополнительно: `cancelled`, `failed`, `uncertain`. Частичные результаты сохраняются.

Java хранит авторитетное состояние кампании, резервации, экземпляры и квитанции
шагов в `SavedData`; изменения отмечаются dirty и сохраняются с миром.
Python SQLite хранит наблюдения, гипотезы, планы и аудит общения.
Только сервер подтверждает, что событие произошло. Механизм сохранения:
[NeoForge SavedData 1.21.1](https://docs.neoforged.net/docs/1.21.1/datastorage/saveddata/).

Повтор одинакового `request_id` возвращает прежний результат; другой payload
с тем же ID отклоняется. Изменение экземпляра требует ожидаемой ревизии.
После восстановления резервной копии создаётся новая эпоха соединения, устаревшие
запросы и планы отвергаются; SQLite сверяется с фактически восстановленным миром.
Нельзя считать, что внешний журнал новее сохранения и потому всегда прав.

Запись перед действием и маркеры этапов снижают риск повторения, но `SavedData`
и разрушение мира не образуют одну атомарную транзакцию с SQLite. Если сервер
упал после взрыва до достоверной квитанции, состояние становится `uncertain`;
автоматически повторять разрушительный шаг нельзя. Дальше — проверка сервером
или решение оператора. Не обещаем «exactly once» для нативной катастрофы после сбоя.

Отмена означает остановку будущих шагов. Уже запущенный метеорит, поток взрыва,
радиация и вторичные эффекты требуют своих проверенных способов остановки;
их успешная остановка подтверждается отдельно. Отмена MCP-запроса сама по себе
не отменяет долговременную операцию в мире:
[семантика отмены MCP](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation).

Откат катастрофы — восстановление согласованной резервной копии, включая мир,
инвентари и контейнеры. Это не универсальная обратная команда. Для автоматических
необратимых профилей сначала требуется проверенная процедура резервирования
и восстановления в отдельном тестовом мире.

При недоступной модели уже принятые допустимые операции продолжаются по серверным
правилам; новых предложений нет. При отключении gateway сервер остаётся автономным.
Отдельный операторский переключатель запрещает новые сценарные запуски и отменяет
ожидающие шаги; он не маскирует уже запущенные эффекты как отменённые.

## 7. Минимум телеметрии и памяти

Снимок имеет `campaign_id`, `world_epoch`, `campaign_revision`, время наблюдения,
стадию, климат, окно восстановления, оценку нагрузки и список известных регионов.
По команде: недавние потери, прогресс исследований, результат столкновений и
оценка готовности. По региону: последний визит, известные очаги, маршрут,
оценка укреплений, признаки подготовки. Полный NBT сундуков не нужен.

Каждый факт несёт источник и давность; оценка отделена от подтверждения.
Таблицы SQLite: наблюдения, сводки регионов, операции, предложения, серверные
квитанции, оценка результата. Вводятся ограничение размера, свёртка старых событий
и фильтр по кампании. Отдельно сохраняется причина выбора сценария кратким
объяснением, без требования хранить внутренние рассуждения модели.

Успех стратегии оценивается не только потерями игроков: разнообразие, контригра,
заметность предвестников, нагрузка и восстановление тоже входят в оценку.
Модель может запомнить «северный отвлекающий манёвр раскрыт датчиками» и выбрать
иной шаблон. Она не обязана каждый раз усиливать противника или наказывать
эффективную защиту, лишая технологическое развитие смысла.

## 8. Порядок включения и испытания

1. Ручной запуск разрешённых примитивов через операторскую команду Java-мода.
2. MCP preview и предложения в теневом режиме: журналируем, не исполняем.
3. Автоматическое исполнение двух лёгких шаблонов с фиксированной политикой.
4. Условные многошаговые операции и долговременная память.
5. Отдельное разрешение измеренных тяжёлых профилей HBM.

Проверки: дубль и конфликт ID, устаревшая эпоха, две конкурирующие заявки,
смерть игрока перед исполнением, выгрузка чанка, перезапуск между шагами,
неизвестный параметр, попытка подставить команду вместо ID, просроченное окно,
ошибка JSON/тайм-аут модели, отмена после предупреждения и сбой после эффекта.
Для нативного взрыва отдельно воспроизводится состояние `uncertain`.

Критерий первой готовности MCP: выключение Python и модели не роняет сервер,
повтор заявки не дублирует событие в штатном сеансе, ARBITER отклоняет запрещённую
цель, а игроки могут заметить и сорвать разрешённую операцию.
