# Второй ИИ: проверка предложения режиссёра

Проверяемая конфигурация: основной Qwen3.5-4B Q4_K_M и критик
Qwen3.5-2B Q4_K_M на CPU. Host поддерживает оба режима; по умолчанию включена
одна модель. Рабочая установка автоматически на dual не переключается.
Её наличие само по себе не доказывает лучшего выбора: модели одного семейства
могут повторять ошибки друг друга. Нужен сравнительный тест с одной моделью.

## Конечный протокол

1. Сервер создаёт цель и список допустимых вариантов со своими лимитами.
2. Режиссёр выбирает допустимый индекс. Это исходный вариант A.
3. Критик видит тот же публичный снимок и предложение, проверяет повторение
   атак/сезон/давление и возвращает согласие или другой допустимый индекс.
4. При несогласии и оставшемся времени режиссёр один раз пересматривает выбор.
   При согласии пересмотр не нужен. Ошибка/таймаут критика или пересмотра
   сохраняет исходный A, а не неподтверждённое предложение критика.
5. Сервер повторно валидирует решение и ставит одну операцию в очередь.

Ответ критика — ограниченный JSON: индекс и до трёх уникальных кодов причин из
enum (`recent_failure`, `repetition`, `pressure`, `season`, `better_alternative`).
Это краткое объяснение предложения, а не внутренние рассуждения модели.
Ни одна модель не получает консоль, игровые координаты, секреты или прямой спавн.
Численность волн/лимиты/тайминги исполнения по-прежнему рассчитывает код.

Один общий deadline оставляет время повторной серверной проверке:
текущая цель живёт 120 секунд активной кампании. Три последовательных запроса
с индивидуальным timeout90 могут не успеть. Общий предел равен меньшему из
`budget_seconds` (не более90) и оставшегося TTL при20тиках/сек минус
`margin_seconds` (по умолчанию5сек). Абсолютный срок передаётся каждому запросу
Ollama, включая проверку digest и чтение ответа; после каждого этапа записывается
оставшийся бюджет. Запросы выполняются последовательно, максимум три.

Итоговый choice вместе с краткими метриками сохраняется перед отправкой серверу.
Схема durable journal не меняется: неизвестная доставка повторяет тот же запрос
и тот же выбор без нового council. До сохранения итогового choice сервер ещё
ничего не получил; при прерывании на этом этапе допускается новый расчёт.
Первый proposal отдельно перед критикой не checkpoint-ится. Ошибка самого A
оставляет прежний штатный fallback на первый серверный вариант.

## Включение и метрики

С5.5.1 в админке: **Обзор → Модель и решения → 1 модель /2 модели**.
Настройка сохраняется в `director/runtime/ai-control.sqlite3` рядом с журналом
решений и имеет приоритет над `ai_mode` из TOML. Остальные параметры и pin
по-прежнему берутся из конфигурации. Admin и host должны использовать одну
папку runtime; для host её определяет `--journal`. Обновить нужно оба Python
процесса, игровой сервер перезапускать не требуется.

Host подхватывает выбор без перезапуска: при простое — примерно за1сек,
при генерации — на границе текущего запроса (его timeout до90сек).
После перехода на single следующие critique/revision пропускаются, остаётся
исходное предложение. Уже сохранённые и отправленные решения не пересчитываются.
При повторном включении dual модели используются по запросу, без предварительной
загрузки обеих в память. Preview по-прежнему работает с одной моделью.

При single отправляется штатная выгрузка только настроенного критика;
его реальный alias определяется по закреплённому digest в `/api/ps`.
`/api/generate` без prompt с `keep_alive=0` освобождает runner, после чего
отсутствие digest повторно проверяется через `/api/ps`. Основная модель
не выгружается этим действием. Совпадающие primary/critic pin отклоняются.
Host повторяет неподтверждённую выгрузку, пока single выбран.
[Ollama: generate/keep_alive](https://docs.ollama.com/api/generate),
[список загруженных моделей](https://docs.ollama.com/api/ps).

Панель отдельно показывает сохранённый выбор, подтверждение host и память.
Состояние «Применено» для single требует подтверждения host и отсутствия
критика в Ollama. При недоступном API выгрузка остаётся неподтверждённой.
Текущая генерация не обрывается посередине: виден статус ожидания.
ОС может сохранять освобождённые файловые страницы как вытесняемый кеш;
это не продолжающая работать модель.

GET `/api/ai-mode` только читает состояние. POST того же маршрута доступен
человеку с same-origin/nonce, принимает mode, UUID запроса и expected_revision.
Конфликт старой вкладки не меняет новый выбор; повтор неизвестной отправки
не создаётся автоматически. В MCP такого переключателя нет.

[Проверка на настоящей2B и память](../verification/ai-mode/README.md).

`director/director.example.toml` содержит оба проверенных pin. Достаточно явно
выбрать `ai_mode = "dual"` для live host. Это отдельная настройка от
`--mode live|preview`: preview всегда использует только основную модель.
Старый TOML без ai_mode/critic/council продолжает работать как single.

Если модель критика ещё не загружена, в том же Docker engine/контейнере:

```sh
docker exec dead-earth-ollama ollama pull qwen3.5:2b-q4_K_M
docker exec dead-earth-ollama ollama cp qwen3.5:2b-q4_K_M dead-earth-critic:2b-q4
```

Перед включением host проверяет alias по закреплённому digest. На данном ПК
используется Docker внутри Ubuntu: команды выполняются через
`wsl -d Ubuntu -u root -- docker ...`. Наличие Windows Docker CLI само по себе
не означает доступность Docker Desktop engine; `model.ps1` пока не выбирает
автоматически WSL при установленном, но неработающем native CLI.

```toml
ai_mode = "single" # либо "dual" при явном включении
poll_seconds = 30

[council]
budget_seconds = 90
margin_seconds = 5

[model]
url = "http://127.0.0.1:11434"
model = "qwen3.5:4b"
digest = "d8b0f5e9760cd1682034f292d7ef72ec46f432149be0df7574bf2d6e92e38c04"

[critic]
url = "http://127.0.0.1:11434"
model = "dead-earth-critic:2b-q4"
digest = "1e2d21a4f03ab9e4a9c1976a4b7e88f21de61d65f2c5485d8fde8942be73f1e7"
maximum_tokens = 96
```

Оба endpoint обязаны совпадать; в dual не более4потоков и context4096.
Каждый запрос задаёт `num_gpu=0`, `think=false`, `keep_alive=0`. Контейнер
ограничивает `OLLAMA_MAX_LOADED_MODELS=1` и `OLLAMA_NUM_PARALLEL=1`.
Alias критика указывает на тот же проверенный manifest, что
`qwen3.5:2b-q4_K_M`; плавающий tag без совпадения digest не принимается.

Критик возвращает, например,
`{"option":1,"reason_codes":["repetition","better_alternative"]}`.
Неизвестные/повторные reason_codes, лишние ключи и недопустимые индексы отклоняются.
Публичный context остаётся прежним; новая аналитика операций в этом срезе
моделям не передаётся.

`metrics` council содержит `ai_mode`, `elapsed_ms`, `remaining_ms`,
`proposal_option`, `final_option`, `outcome`, `revision_count` (0или1) и `stages`
(до3). Этап содержит `stage` (`proposal|critique|revision`), model/digest,
`status` (`valid|error|skipped`), elapsed/remaining_ms, допустимый option,
reason_codes и доступные prompt/output_tokens. Ошибка — только ограниченный
`error_code`; raw chat, thinking и свободные объяснения не сохраняются.
Ошибка A также сохраняет краткую стадию в метриках штатного fallback.

## Память этого ПК

18 октября проверены 31.84 ГиБ физической ОЗУ (номинально32), Xeon E5-2678v3,
RTX2060 SUPER8GiB. Клиент Prism ограничен heap6GiB; установленный сервер —
heap6GiB. JVM также требует нативную память сверх heap.

Предыдущий [нагрузочный тест](performance/2026-10-18-load-test.md) использовал
heap сервера5GiB/клиента6GiB и одновременно работавший CPU-режиссёр.
Минимум свободной физической памяти около5.7GiB. Это свидетельство для старой
версии/измеренных сцен, не доказательство любых будущих шести игроков/больших баз.

Оценочный бюджет для игры (не измерение одновременного worst case):

| Назначение | Резерв ОЗУ |
|---|---:|
| Windows, фоновые приложения, служебные процессы | 7GiB |
| Клиент: heap6 + нативная память | 8GiB |
| Сервер: heap6 + нативная память | 7GiB |
| Обе модели с поочерёдной загрузкой в одном контейнере | до6GiB |
| Остаток от31.84GiB | около3.8GiB |

Предпочтительный режим: `OLLAMA_MAX_LOADED_MODELS=1`,
`OLLAMA_NUM_PARALLEL=1`, `keep_alive=0`, контекст4096, суммарно4CPU/6GiB.
Обе модели хранятся на диске, но одновременно загружена одна. Это соответствует
последовательному обсуждению; запуск двух постоянных контейнеров не требуется.
Видеопамять остаётся клиенту. Ошибка загрузки/работы критика сохраняет A.
Превентивного guard по свободной RAM/TPS в этом Python host пока нет;
ограничения памяти задаёт контейнер.

Текущий `.wslconfig` разрешает Ubuntu до31GB при `swap=0`. Это верхний предел,
не предварительное резервирование, но он допускает чрезмерный рост WSL рядом
с игрой. Для игрового профиля с одним AI-контейнером стоит ограничить WSL
примерно10–12GiB после завершения обучения. Это постоянная настройка с
перезапуском WSL; при этой проверке она не менялась.

QLoRA обучение — отдельная нагрузка: исходные FP16 веса, optimizer/cache и
CUDA не включены в игровой бюджет. Одновременная игра с обучением не подтверждена
и не требуется для работы двух CPU-моделей.

## Перед включением

Закрепить digest второй модели; проверить фактические working set, время
полного раунда, JSON-контракт и повторение атак. Затем сравнить одну/две модели
на одинаковом наборе и провести короткий совместный игровой замер с guard по
свободной RAM и TPS. Замеры синтетического обмена без клиента/сервера не выдаются
за такой интеграционный тест. Проверка не устанавливает второй ИИ в production.
